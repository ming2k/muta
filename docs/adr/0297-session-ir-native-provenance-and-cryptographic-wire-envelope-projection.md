# 0297. Session IR Native Provenance, Cryptographic Wire Envelope Projection, and Lossless Heterogeneous Degradation

- **Status:** Accepted
- **Date:** 2026-03-31
- **Scope:** `muta-contracts` (`SessionIR`, `Message`, `provider_meta`), `muta-llm-client` (`protocol::google`), `muta-persistence` (`causal_nodes`, `payload_json`), `muta-agent` (`orchestration`, `rounds`)

- **Amends:** [ADR-0161](0161-route-scoped-inference-protocols-and-prompt-cache-contracts.md) (inference protocols and prompt cache contracts)

## Context and Problem Statement

When converting conversations from standard Chat Completion protocols (e.g. OpenAI format, Claude, or third-party gateways) to Google Gemini (`generateContent` with Gemini 2.5/3.x thinking models), or when resuming multi-turn conversations where prior tool calls were generated by a non-Gemini provider, Google's API abruptly aborts with HTTP 400:

```json
{
  "error": {
    "code": 400,
    "message": "Function call is missing a thought_signature in functionCall parts. This is required for tools to work correctly, and missing thought_signature may lead to degraded model performance. Additional data, function call `default_api:run_command` , position 638. Please refer to https://ai.google.dev/gemini-api/docs/thought-signatures for more details.",
    "status": "INVALID_ARGUMENT"
  }
}
```

### The Architectural Root Cause

Modern reasoning models enforce cryptographic integrity over their internal chain of thought:
1. **Google Gemini Thinking Models (2.5 / 3.x)**: Emit an opaque, server-signed token (`thought_signature` or `thoughtSignature`) inside `functionCall` or `thought` parts whenever the model invokes a tool. Google's server-side validator mandates that **every subsequent request replaying that tool call must echo the exact cryptographic signature**.
2. **OpenAI Chat Completion Protocol Standard**: Defines only `id`, `name`, and `arguments` in `tool_calls`. It has no semantic slot for vendor cryptographic tokens.
3. **Flawed Assumption of Upstream Leniency**: The initial implementation assumed Google would tolerate unsigned `functionCall` parts when history lacked signatures (evidenced by unit test `preserves_unsigned_tool_calls_as_structured_function_calls` in `crates/muta-llm-client/src/protocol/google/request.rs`). In production, Google's backend strictly rejects requests carrying unsigned `functionCall` parts with `400 INVALID_ARGUMENT`.
4. **Leaky Abstraction Anti-Pattern**: Attempting to inject Google's proprietary `thought_signature` into OpenAI-compatible `tool_calls` schemas pollutes neutral interfaces with ephemeral transport baggage. Conversely, dropping foreign tool calls destroys conversational and causal continuity.

We require an uncompromised, clean-break architectural resolution founded on **Session IR Native Provenance** and **Projection Policy**.

---

## Decision Drivers

1. **Zero Leaky Abstraction**: Neutral Session IR and OpenAI-compatible schemas must remain pure semantic specifications. Vendor-proprietary cryptographic tokens (`thought_signature`, Anthropic thinking signatures) must never pollute cross-provider core models.
2. **Irreversible Cryptographic State**: A server-signed HMAC or asymmetric signature is non-reproducible. It exists only at wire ingress. If not captured at the seam and committed durably into the turn envelope, it cannot be reconstructed.
3. **Lossless Homogeneous Replay**: When a conversation continues under the same provider that originated the signature, the compiler must emit native, signed wire structures (`functionCall` + `thoughtSignature`), preserving KV-cache alignment and reasoning continuity.
4. **Deterministic Heterogeneous Degradation**: When projecting history into a provider with strict cryptographic admission rules (Google Gemini), any historical tool execution lacking a valid signature MUST NOT be submitted as an unsigned native `functionCall`. It must be projected as an objective natural language dialogue fact, preserving epistemic truth while bypassing the server-side cryptographic barrier.
5. **Transcript and Causal Graph Immutability**: Historical facts in `CausalGraph` are immutable (ADR-0275). Projection adaptation is a pure lowering transformation; it must never mutate the underlying stored nodes.

---

## Considered Options

- **Option 1: Pollute OpenAI / Universal Schema with Vendor Metadata.** Inject `thought_signature` into `ToolCall.extra` or universal JSON fields.
  - *Verdict*: **Rejected**. Severe leaky abstraction. Breaks schema compatibility, couples all models to Google's internal transport details, and fails when history originated from a third-party model (e.g. GPT-4o) that never possessed a Google signature.
- **Option 2: Dummy / Synthetic Signatures.** Fabricate dummy tokens (e.g. `"context_engineering_is_the_way_to_go"`).
  - *Verdict*: **Rejected**. Fragile hack. Google actively validates cryptographic integrity; forged tokens fail server-side HMAC checks and trigger unpredictable degradation or outright rejection.
- **Option 3: Elide / Drop Historical Unsigned Tool Calls.** Strip tool calls from messages missing signatures.
  - *Verdict*: **Rejected**. Directly destroys conversational context, hallucinates broken causal lineage, and breaks agent reasoning on multi-step tasks.
- **Option 4 (Chosen): Two-Layer Provenance Architecture with Safe Semantic Degradation.**
  - Store immutable semantic facts in Session IR (`ir`) and wire artifacts in a sidecar envelope (`envelope.artifacts` / `provider_meta`).
  - Wire ingress captures and persists the signature at receipt.
  - Request compiler performs target-aware lowering:
    - If tool call has valid signature $\rightarrow$ lower to native `functionCall` with `thoughtSignature`.
    - If tool call lacks signature (heterogeneous model switch or unsigned legacy) $\rightarrow$ degrade to natural language dialogue facts (`[Executed tool "..." with arguments: ...]` in `model` role, `[Tool result for "..."]:` in `user` role).

---

## Decision Outcome

Chosen option: **Option 4**. We formalize the two-layer provenance and degradation contract across contracts, persistence, and protocol lowering.

### 1. The Two-Layer Session Model

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        Session IR Node / Message                       │
├────────────────────────────────────────────────────────────────────────┤
│ 1. Canonical Semantic AST (Neutral, Cross-Provider)                    │
│    - Role: User / Assistant / Tool                                     │
│    - Content: Text blocks, Tool calls (id, name, args), Tool results   │
├────────────────────────────────────────────────────────────────────────┤
│ 2. Wire Envelope Provenance (Sidecar: `provider_meta`)                 │
│    - Origin Provider: "google" | "anthropic" | "openai"                │
│    - Artifacts: { "gemini_thought_signatures": { "<id>": "<sig>" } }   │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                    Target Provider Lowering (Pass 4)
                                    │
                    ┌───────────────┴───────────────┐
      Target == Origin && Has Signature     Target != Origin || Missing Signature
                    │                                       │
     ┌──────────────▼──────────────┐         ┌──────────────▼──────────────┐
     │  Homogeneous Native Lowering│         │ Safe Semantic Degradation   │
     │  - functionCall + signature │         │ - Model: [Executed tool …]  │
     │  - functionResponse         │         │ - User:  [Tool result …]    │
     │  (Full Reasoning Continuity)│         │ (Zero 400s, Full Context)   │
     └─────────────────────────────┘         └─────────────────────────────┘
```

### 2. Ingress Wire Capture & Durable Persistence
- When Google Gemini emits candidate parts:
  - If a part contains `thought_signature` or `thoughtSignature`, `muta-llm-client::protocol::google::response` binds it to both `call.id` and `call.name` in `THOUGHT_SIGNATURES_META_KEY`.
  - In streaming mode, `ProviderStreamEvent::Completed` transfers terminal `artifacts` to `ProviderCompletionMeta`.
  - In `muta-agent::agent::rounds`, terminal completion artifacts are stored in `Message.provider_meta`.
  - `muta-persistence` serializes `Message` into `causal_nodes.payload_json`. Cold restarts and session resumes preserve the exact cryptographic signature.

### 3. Pass 4 Target Lowering in Session IR Compiler (`muta_contracts::session_ir::compiler`)
As mandated by ADR-0241, Pass 4 of the request compiler pipeline is the authoritative domain layer for target dialect lowering:
1. When compiling a session request with `CompilerOptions.target_dialect` pointing to Google (`google`, `gemini`, `google-gemini`), Pass 4 inspects historical dialogue messages:
   - For `Role::Assistant` with tool calls:
     - Calls verified by `message.has_gemini_thought_signature_for(&call)` are retained as native structured tool calls.
     - Calls lacking a signature (from cross-provider model switching or foreign completion imports) are lowered directly into objective dialogue fact prose:
       ```text
       [Executed tool "<name>" with arguments: <args>]
       ```
       and removed from `tool_calls`.
   - For `Role::Tool`:
     - If the corresponding assistant tool call was degraded, the tool result is lowered into an objective user-role dialogue fact:
       ```text
       [Tool result for "<name>"]:
       <content>
       ```
       and `tool_call_id` is cleared.
2. The emitted `ModelRequest` is therefore already 100% normalized and compliant with Google's cryptographic invariants before entering the network layer.

### 4. Defense-in-Depth Wire Serializer Enforcement (`protocol::google::request`)
At the network serialization seam in `muta-llm-client`:
- Even for direct requests that bypass `SessionIR` (e.g. ad-hoc subagent calls or test fixtures), the serializer maintains `signed_calls: &mut HashSet<String>`.
- Any tool call lacking a cryptographic signature is degraded to a text part; any tool response lacking a signed call reference is degraded to a user text part.
- Unsigned `functionCall` parts are strictly forbidden from crossing the HTTP wire.

---

## Invariants & Behavioral Boundaries

- **`[INV-PROV-01]` Zero Leaky Abstraction**: Public contracts (`ToolCall`, `SessionIR`, `Message`) must never incorporate vendor-specific signature parameters into their top-level canonical fields.
- **`[INV-PROV-02]` Durability at Wire Ingress**: Any opaque cryptographic state emitted by an upstream provider must be captured immediately at protocol parsing and persisted durably in `provider_meta`.
- **`[INV-PROV-03]` No Unsigned Function Calls to Google**: The Google request compiler MUST NEVER emit a `functionCall` part that lacks a `thoughtSignature`. Doing so is a verified HTTP 400 violation.
- **`[INV-PROV-04]` Lossless Degradation**: Degrading an unsigned tool call to natural language text must preserve the exact tool name, arguments, and result output byte-for-byte. No historical evidence may be omitted.
- **`[INV-PROV-05]` Pass 4 Dialect Lowering Authority**: Dialect-specific context projection must execute within Pass 4 of `compile_session_request` (`muta_contracts::session_ir::compiler`), guaranteeing that `ModelRequest` instances satisfy target dialect invariants prior to provider dispatch.

---

## Positive Consequences

1. **Immunity to HTTP 400 Failures**: Completely eliminates the `Function call is missing a thought_signature` fatal error across all multi-turn sessions.
2. **Seamless Cross-Model Switching**: Users can start a session on Claude or GPT-4o and hot-switch to Gemini 2.5/3.x mid-session without corrupting or dropping history.
3. **Pristine Domain Models**: Core Session IR and database schemas remain free of vendor-specific pollution.
4. **Cold-Start Resilience**: Resuming a Gemini session from SQLite rehydrates original thought signatures, maintaining unbroken native tool calling.

---

## Negative Consequences & Trade-offs

- Heterogeneous turns (tool calls initiated by Claude/GPT replayed to Gemini) lose native structured call parsing on the upstream side and are perceived by Gemini as assistant self-reports. This is technically unavoidable because only Google can sign Google thought signatures.

---

## Rejected Alternatives & Negative Knowledge

### Rejected: Injecting Synthetic or Fixed Signatures
- **Hypothesis**: Send a static token like `"context_engineering_is_the_way_to_go"` or base64 dummy string.
- **Failure Mode**: Google validates cryptographic signatures against internal session seeds. When the server validates the HMAC or timestamp, it rejects invalid signatures with `INVALID_ARGUMENT`.

### Rejected: Dropping Unsigned Tool Calls from Context
- **Hypothesis**: If a tool call cannot be signed, omit it from history sent to Gemini.
- **Failure Mode**: The model loses epistemic awareness of file reads, command executions, and tests already run, leading to infinite repeat loops and catastrophic task failure.
